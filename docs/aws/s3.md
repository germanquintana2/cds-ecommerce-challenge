## Seguridad aplicada

- Los cuatro controles de Block Public Access están activados.
- Object Ownership es `BucketOwnerEnforced`: ACL desactivadas.
- Cifrado predeterminado SSE-S3 (`AES256`).
- La política de [s3-bucket-policy.json](./s3-bucket-policy.json) deniega operaciones por HTTP a principales que no sean servicios de AWS. No concede acceso a nadie. La excepción de principales de servicios sigue la recomendación de AWS para evitar bloquear llamadas entre servicios cuyos datos de transporte pueden estar omitidos.
- No se habilitó versionado, hosting web ni CORS. La aplicación sube imágenes desde el backend; no requiere cargas directas del navegador a S3.
- No se generaron claves de acceso permanentes ni se modificaron permisos del rol gestionado por AWS.

## Configuración de la aplicación

Estos valores no son secretos. Ya están contemplados en `.env.example`; el evaluador debe configurar su propio bucket y acceso:

```dotenv
AWS_REGION=us-east-2
S3_BUCKET_NAME=cds-challenge-german-647432778236
AWS_PROFILE=cds-challenge
```

El perfil local usa credenciales temporales obtenidas con:

```sh
aws login --region us-east-2 --profile cds-challenge
```

Este perfil tiene permisos amplios de administración del proyecto. Se utilizó para preparar y probar infraestructura; no representa una identidad de producción limitada al bucket. Antes del despliegue se definirá la identidad del backend con permisos mínimos para subir, leer y eliminar objetos bajo `products/`. No se deben copiar las credenciales del perfil al frontend ni al repositorio.

## Integración implementada

- Handler `POST /api/uploads/products` con sesión ADMIN y comprobación de origen; las escrituras de datos siguen pasando por procedimientos tRPC protegidos.
- Límite de cuerpo multipart de 6 MB y de archivo de 5 MB, aplicado también a cuerpos enviados en chunks.
- JPEG, PNG o WebP con tipo declarado y contenido real coincidentes; Sharp rechaza archivos inválidos, animaciones e imágenes de más de 16 megapíxeles.
- Conversión a WebP y límite de 2000 × 2000, sin ampliar imágenes pequeñas.
- Nombres únicos bajo `products/<productId>/`, cifrado AES256 y metadata que vincula el objeto al producto.
- Clave del objeto en PostgreSQL; se verifica el objeto en S3 antes de asociarlo.
- Enlaces de lectura de 15 minutos generados en cada consulta, sin persistirlos ni usar caché de optimización de imágenes. Su vigencia no puede superar la de las credenciales.
- Limpieza best effort de imágenes reemplazadas y de subidas que no se pudieron asociar. No hay una tarea automática para huérfanos por fallos de red o limpieza; ver [prueba manual](../pruebas-productos.md).

## Verificación realizada

- Región, bloqueo público, cifrado y ownership consultados mediante API.
- `IsPublic: false` confirmado.

## Portadas de categorías

Las categorías admiten imágenes propias bajo `categories/<uuid-categoria>/<uuid-imagen>.webp`, con metadata `categoryid`. Se aplica la misma validación, normalización WebP, cifrado y lectura firmada que a productos. La subida exige ADMIN y verificación de origen; el guardado comprueba el prefijo y la metadata con HeadObject. En un despliegue con permisos restringidos, incluir también `categories/*` en los permisos S3 del backend. No se hacen públicas las imágenes.
